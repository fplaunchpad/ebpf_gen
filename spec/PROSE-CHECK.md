# Cross-check: generated prose vs RFC 9669 and CONSTRAINTS.md

**What this is.** A by-eye comparison of the generated document
`spec/out/isa-alu.md` against (a) RFC 9669 §4.1 and (b) `fstar/CONSTRAINTS.md`,
recorded so a reviewer can repeat it. **It is a human-review artifact, not a
proof.** Nothing here is machine-checked except the anchors listed in §4; a
statement below marked "agrees" means one reader compared two texts and found
them to say the same thing, which is exactly the kind of claim the rest of
this project replaces with proofs. The value is the *other* column: the list
of places where the generated prose is weaker, noisier or silent compared
with the RFC's own wording (§3). That list is a finding about what a spec DSL
of this shape can and cannot generate, and it is meant to feed back into the
DSL design — not to be papered over.

## 0. Method, and how to repeat it

```sh
make -C spec prose      # regenerates spec/out/isa-alu.md from spec/ebpf_alu.kspec
make -C spec test       # 36 assertions, incl. staleness + coverage + content anchors
```

Compared, on 2026-08-08:

| side | what was read |
|---|---|
| generated | `spec/out/isa-alu.md` §2 (72 instruction sections), §3 (encoding table), §4 (excluded forms) |
| RFC 9669 | §4.1 "Arithmetic instructions": the opcode/offset/description table, the operand-width paragraph, the shift-mask sentence, the signed-modulo sentence, the MOVSX sentence, the byte-swap rows (fetched from `rfc-editor.org`; **positive** quotations only — see P2 for why one negative observation is recorded as a flag rather than a finding) |
| repo | `fstar/CONSTRAINTS.md` C1–C17 (esp. C5, C8, C10, C11, C12, C13, C14), `fstar/Ebpf.Semantics.fst` header, `fstar/Ebpf.Int.fst`, `ir/SPEC.md` §3 (mnemonics) |

Two artifacts per instruction are compared separately, because they do not
have the same quality: the **pseudocode** line (`dst = …`), which is close to
the RFC's description column, and the **English sentence**, which is the
structural rendering. Where they diverge in quality it is noted.

Terminology note: `spec/DESIGN.md` §5 calls the prose backend "MS4" and the
encoding backend "MS3"; the milestone plan actually executed makes prose MS3.
Same backend, different label — recorded here rather than by editing DESIGN.

### Encoding cross-check (mechanical, and it passes)

The RFC's `code` column maps to the generated `opc` byte as `code << 4`, and
every row of §3 of the generated document matches: ADD 0x0/0x00, SUB
0x1/0x10, MUL 0x2/0x20, DIV 0x3/0x30, OR 0x4/0x40, AND 0x5/0x50, LSH
0x6/0x60, RSH 0x7/0x70, NEG 0x8/0x80, MOD 0x9/0x90, XOR 0xa/0xa0, MOV+MOVSX
0xb/0xb0, ARSH 0xc/0xc0, END 0xd/0xd0; `offset = 1` selects SDIV/SMOD;
`offset = 8/16/32` selects the MOVSX width; class `ALU` = 0x04, `ALU64` =
0x07, source `X` = 0x08. The three byte-swap examples in the RFC land on
0xd4 (`{END, LE, ALU}`), 0xdc (`{END, BE, ALU}`) and 0xd7
(`{END, TO, ALU64}`), which are exactly the generated opcodes. This part of
the document needed no interpretation to check — it is data, and
`tests/run.sh` already anchors seven of these rows against
`Ebpf.Serialize`'s own `assert_norm` values.

## 2. What went right, and why it is not obvious

Worth recording because it is the part that transfers to other DSLs:

- **One rule, two constraints.** "A result declared `bits n` written into a
  64-bit register clears bits *n*..63" is a single line in the backend. It
  generates C10 for every ALU32 form *and* C14's truncate-to-width for the
  16/32-bit byte swaps, and it cannot be forgotten for a future instruction,
  because it is keyed on the declared result type rather than on the
  instruction.
- **The sign of `/` is derived, not asserted.** `Ebpf.Int.fst` says F*'s `/`
  and `%` on `int` are Euclidean. The backend runs the same syntactic sign
  analysis that K5 uses, so `wrap n (d / pow2 (s % n))` (RSH) renders as "the
  unsigned quotient …" while `wrap n (sval n d / pow2 (s % n))` (ARSH)
  renders as "…, rounded toward negative infinity" — the arithmetic-shift
  behaviour falls out of the AST instead of being an English claim about it.
  If someone deleted the `sval` from ARSH's `sem` cell, the prose would stop
  saying it, in the same edit.
- **The exclusion is a positive claim.** RFC 9669 states MOVSX's valid
  widths per class and leaves `(ALU, 32)` to be inferred from a list; the
  generated §4 states the excluded point, the `valid` predicate that yields
  it, and a reason, and K6 forces the two to agree. `CONSTRAINTS.md` C13
  records that the F* model's own guard is a tautology here — this document
  is where a reader sees the intended rule stated instead.
- **The `!=` normalisation earns its keep.** `if s = 0 then 0 else …` in the
  spec source prints as `(src != 0) ? … : 0`, which is the RFC's own idiom,
  so the DIV/SDIV/MOD/SMOD rows can be compared with the RFC by eye without
  mentally inverting a branch.

## 3. Findings: where the generated prose is weaker than the RFC

Each finding names the cause in the DSL/IL and a candidate fix. P1–P6 are
about wording; P7–P9 are places the **IL does not carry the information**
needed for faithful prose, which is the part that should feed back into the
`.kspec` grammar; P13 is a template that is sound for this fragment but not
for every expression the grammar admits.

**P1 — shifts are rendered as multiply/divide by a power of two.** RFC:
`dst <<= (src & mask)`. Generated: "the product of the destination value and
2 raised to the power (the unsigned remainder of the source register value
divided by 64), truncated to 64 bits". Two gaps: the word *shift* never
appears, and `% 64` is not `& 0x3F` — they coincide only because the widths
are powers of two, an equivalence the reader must supply. *Cause:* the
combinator set is exactly `Ebpf.Int` + `FStar.UInt`, and the F* model has no
shift combinator (it multiplies and divides by `pow2`). *Fix:* either add
`shl`/`shr` combinators that print to the same F* terms, or let an entry
carry a rendering hint. The second is cheaper and dishonest in the way this
project is trying to avoid — a hint is authored prose again — so the first is
the right answer if this matters.

**P2 — C12's corner case is implied, not stated.** RFC 9669 §4.1 requires
truncated signed division/modulo (`a % n = a - n * trunc(a / n)`). No sentence
about signed *overflow* — most-negative divided by −1 — turned up in the
§4.1 text read for this check. `CONSTRAINTS.md` C12 states "INT64_MIN/-1 =
INT64_MIN, smod → 0" and cites "RFC 9669"; that behaviour certainly follows
from truncated division plus the 64-bit register width, so if the RFC really
is silent then C12's citation is over-attributed — the claim would be right
and the source would be the composition rather than the text.

**This is an unverified negative claim about an RFC's contents and nothing has
been changed on the strength of it.** `fstar/CONSTRAINTS.md` is untouched;
the item is logged for someone to confirm against the primary source, and a
negative ("the text does not say X") is exactly the kind of claim that needs
the document in hand rather than a search. Recorded here as a flag, not a
finding.

The generated prose is in the same position one level down: it
says "…, truncated toward zero), reduced modulo 2^64 (two's-complement
wrap-around)", from which the corner case follows in one step, and never
spells it out. *Cause:* the AST has no notion of a distinguished input; the
obvious fix — evaluating each `sem` at corner inputs and tabulating the
results — needs arithmetic modulo 2^64, and `specgen` is deliberately
stdlib-only OCaml whose native `int` is 63-bit. Recorded as a deliberate
non-goal; a bignum dependency for a documentation table is the wrong trade.

**P3 — C10 is split across two lines where the RFC has one formula.** The
RFC's `(u32)` casts say "truncate the operands *and* the result" in one
expression. The generated section says the operand part under **Reads**
("read as a 32-bit value (its low 32 bits)") and the result part under
**Writes**. Nothing is lost and the split is arguably clearer, but a reader
diffing against the RFC assembles one formula from two bullets. *Cause:*
DESIGN §1 puts operand reading outside the spec on purpose, so the read width
is a property of the read, not of the operation.

**P4 — the immediate rule (C11) is invisible per instruction.** A section for
`sdiv64 dst, imm` says only "`imm` — the 32-bit immediate field, read as a
64-bit operand value (see §1.4)". Whether that read sign-extends (ALU64) or
zero-fills a 32-bit pattern (ALU32) appears **only** in §1.4, which is fixed
scaffolding written by the backend, not derived — and the RFC states it
explicitly, per class, and even distinguishes signed and unsigned operations
when doing so. This is the largest content gap in the document. *Cause:*
`spec/DESIGN.md` §1 deliberately excludes operand reading (`opbits`,
`imm64`/`imm32`) from the spec language. *Fix:* give the DSL a read rule per
(role, axis case), e.g. `read src:imm@n = sext 32 n`; it would remove the
last hand-written arithmetic from `Ebpf.Semantics`, let MS2 generate `opbits`,
and make C11 derivable here. This is the single change that would most
improve the generated document.

**P5 — "register source only" is shown, not said.** For MOVSX the generated
document conveys the register-only restriction structurally: five instances,
each with a `Reads` line naming a register, and the mnemonic `movsx8_64 dst,
src`. It never writes the RFC's sentence "MOVSX is only defined for register
source operands", because the absence of an axis is not a node in the AST.
Related: the `Reads` line says the source is read at 32/64 bits and the
operation then takes "the low 16 bits of" it, where the RFC writes `(s16)src`
directly — one indirection more, faithful to `sext f n s` but wordier. Also
note the exclusion *reason* in §4 is the one piece of English authored in the
`.kspec` itself (a mandatory field), so it is spec text, not generated text.

**P6 — `be32` and `bswap32` produce textually identical operations.** On the
pinned little-endian host `Swap ToBE z` and `Swap Bswap z` have the same
`sem`, so the two sections differ only in their encoding line. That is
correct — the RFC's `{END, BE, ALU}` and `{END, TO, ALU64}` do the same thing
on such a host — but it reads like a generator bug. The fact that makes it
correct (the host pin, `s_host` in the IL) is now appended to every operation
sentence whose `sem` mentions `low` or `bswap`, so `le16` reads "the low 16
bits of the destination value, on the pinned little-endian host" where the RFC
writes `dst = le16(dst)`; the identical `be32`/`bswap32` pair remains, and is
genuinely identical. *Residual fix:* making the host an axis rather than a
global would turn "on a little-endian host" from a note into a form
distinction, which is what it actually is.

**P7 — `*` conflates "operand-carried" with "unused".** `neg64 dst` prints
`imm = *`, but NEG has no immediate operand at all; so does every
register-source ALU form. The kernel requires unused encoding fields to be
zero, and the spec has no way to say that. K8's disjointness check treats `*`
as compatible with anything, so this errs in the safe direction for the
overlap check — but an encoder generated from this IL would have no
instruction to zero those bytes, and the prose is misleading. §1.6 of the
generated document says so out loud. *Fix:* distinguish `0` (must be zero)
from `*` (operand-carried) in the encoding field grammar.

**P8 — the IL carries no assembly mnemonic.** Entry names are `Ebpf.Ast` case
names, so the backend supplies the three stems `le`/`be`/`bswap` itself, and
derives the width suffix by joining the instance's width valuation
innermost-first. That rule yields `movsx8_64` only because `movsx` declares
`width n = bits w, f = bits sz` **in that order**: reordering a `width` line —
a change with no semantic content — would silently rename five instructions.
`tests/run.sh` anchors all eight non-trivial mnemonics against `ir/SPEC.md`
§3, so the drift is caught, but by a test rather than by the design. *Fix:* an
`asm=` attribute on enum cases and an optional mnemonic column on entries.

**P9 — the IL cannot say what does *not* happen.** The RFC states positively
that division by zero sets the destination to zero *instead of* faulting; the
worked target for this milestone likewise wanted "…the result is 0 (no
trap)". The AST says the result is `0`. There is no notion of trapping,
faulting or aborting anywhere in the IL, so the absence of a trap is
unrepresentable: the generated prose conveys it only by exhibiting a total
function. The same limit applies to every "and nothing else happens" claim
(no flags, no side effects, other registers unchanged). *Cause:* the value
semantics is a pure function of the operand values by construction (DESIGN
§1). *Fix:* none proposed — this is a scope boundary, and stating it is more
useful than papering over it.

**P10 — noisier than the RFC: the explicit `mod 2^N`.** RFC: `dst += src`,
with truncation implicit in the register width. Generated:
`dst = ((dst + src) mod 2^64)`. The renderer prints `wrap` wherever the spec
writes it, and cannot tell that `mod 2^64` is load-bearing for `dst + src`
(overflow) and a no-op for `dst / src` — that distinction is a proof, not a
reading. Deliberate: faithful beats pretty, since the point of the artifact is
to show what the model computes.

**P11 — the mode story is scaffolding, not spec.** Every Definedness
paragraph renders the AST condition, but the surrounding sentence ("strict
mode requires a proof …; kernel mode accepts the instruction without one") is
fixed text keyed only on "the condition is not `true`". The two-mode story
lives in `CONSTRAINTS.md`, not in the `.kspec`, which has no notion of modes —
so this is the one place the document asserts something about the checker
that its source does not contain.

**P12 — long signed sentences are the weakest English in the document.** The
SMOD section's operation sentence is ~60 words with three nested "of"
phrases; the pseudocode line above it
(`trunc_mod(signed64(dst), signed64(imm)) mod 2^64`) is unambiguous and much
closer to the RFC. Structural rendering degrades with nesting depth: it is
excellent at depth 2 (ADD, MOV, MOVSX), acceptable at depth 3 (LSH, ARSH) and
poor at depth 4 (SDIV, SMOD). Mitigated by bracketing any sub-phrase that
already contains a comma, and by printing the raw `sem` cell in every section
so the reader always has the short form; not solved.

**P13 — one template is correct for this fragment, not in general.** `/` on a
possibly-negative dividend renders as "…, rounded toward negative infinity".
F*'s `/` on `int` is Euclidean, which coincides with rounding toward −∞ only
when the **divisor is positive**; for a negative divisor Euclidean division
rounds the other way (it keeps the remainder non-negative). Every division in
the current fragment either has a bit-pattern dividend (unsigned) or divides
by `pow2 (s % n)`, which is always positive, so the rendering is correct for
all 72 instructions today — but it would silently become wrong if a future
`sem` cell divided by something that can be negative. Recorded rather than
fixed: the honest fix is to make the template say "Euclidean quotient" and
lose the reading that makes ARSH recognisable as an arithmetic shift, or to
extend the sign analysis to the divisor as well. Found by re-reading the
templates against `Ebpf.Int.fst`, not by a test — which is the point of §4
below.

## 4. What is machine-checked, and what is not

Machine-checked by `make -C spec test` (36 assertions):

- the committed `spec/out/isa-alu.md` is exactly what the current generator
  produces from the current `.kspec` (staleness diff);
- every one of the 72 instance ids and 19 entry ids in the IL appears in the
  document, and the number of instruction sections equals the number of
  instances (no omissions, duplicates or extras);
- eight mnemonics against `ir/SPEC.md` §3;
- seven opcodes against `Ebpf.Serialize`'s own anchors (pre-existing);
- six content anchors, one per constraint discussed above (C5, C8, C10, C12,
  C13, C14), each asserting the *derived* sentence — so changing a `sem` cell
  without re-reading the constraint it implements breaks the build.

**Not** checked by anything: that the English templates say what the
combinators mean. That is the residual trust in this backend, and it is
bounded by the size of the table in §1.2/§1.3 of the generated document —
about twenty templates, each applied uniformly to 72 instructions. The
argument for the design is exactly that: reviewing twenty templates once is a
smaller job than reviewing 72 paragraphs, and the 72 paragraphs cannot drift
away from the semantics between reviews.
